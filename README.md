# MiyKo

MiyKo is a mobile household food agent. A text or audio request starts a long-running managed workflow for dinner, lunch, a two-week shop, meat or a basket change.

## Core loop

```text
login/register → create or join household → household owner connects Silpo once
  → create workflow → LangGraph + Mem0 + Silpo MCP
  → graph pauses for decisions → owner approves/declines
  → same workflow resumes → MCP updates basket or completes order
```

“Add ice cream” is a workflow action. MiyKo does not search or store products locally; the provider MCP returns the current basket, products and images. Recipes can be generated by the LLM or provider assistant. MiyKo stores household identity, permissions, provider connections, workflow references and approval outcomes.

## Ownership

- Expo app: untrusted UI.
- Hono API: auth, RLS, household permissions, provider connection, thin workflow projections, approvals and outbox retries.
- LangGraph Cloud: workflow state, checkpoints, messages, generated recipe and pause/resume.
- LangSmith Cloud: tracing.
- Mem0 Cloud: long-term memory.
- Silpo MCP: provider products, images, basket, fulfillment and order details.
- PostgreSQL/Drizzle: control-plane and thin projection data only; no local recipe/product/order/memory store.

The provider abstraction and registry remain: they isolate provider authentication from the core flow. MCP tool discovery, product and basket operations are handled by the managed workflow after authorization and approval.

MiyKo may cache provider reads or the latest observed workflow/provider status to reduce repeated requests. These are read optimizations only: they are not authoritative state, are not approval evidence and must be revalidated by the managed workflow before a provider mutation.

## Security

Authentication and authorization are enforced at the API and database RLS boundary. Owner approval is required before provider-mutating actions. Provider credentials stay encrypted on the server; Mem0 is context only and cannot grant access or approval. Missing integrations fail explicitly; there are no mock or silent fallback paths.

## Database

The database package contains one clean `drizzle/0000_initial.sql` baseline. It is not executed by API startup. Use the separate migration connection when the database owner explicitly applies it.
