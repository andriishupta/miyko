# MiyKo

Run `pnpm typecheck` from the repository root to type-check every TypeScript workspace. GitHub Actions runs the same command for pushes and pull requests.

MiyKo is a mobile household food agent. A text or audio request starts a long-running managed workflow for dinner, lunch, a two-week shop, meat or a basket change. The same workflow can also support a temporary party, picnic, office event or barbecue.

## Core loop

```text
login/register → create or join household → household owner connects Silpo once
  → create workflow → LangGraph + Mem0 + Silpo MCP
  → graph pauses for decisions → owner/admin approves or declines
  → same workflow resumes → MCP updates basket → owner completes checkout in Silpo
```

“Add ice cream” is a workflow action. MiyKo does not search or store products locally; the provider MCP returns the current basket, products and images. Recipes can be generated by the LLM or provider assistant. MiyKo stores household identity, permissions, provider connections, typed workflow references and approval outcomes.

The MVP is household-first. The same household workflow can be used for a family, office team, party, picnic or another temporary group without changing the workflow model.

## Ownership

- Expo app: untrusted UI.
- Hono API: auth, RLS, household permissions, provider connection, thin workflow projections, approvals and outbox retries.
- Local LangGraph Agent Server for the MVP (hosted later): workflow state, checkpoints, messages, generated recipe and pause/resume.
- Local structured workflow logs: OpenAI and Silpo MCP call evidence without cloud tracing.
- Mem0 Cloud: long-term memory.
- Silpo MCP: provider products, images, basket, fulfillment and order details.
- PostgreSQL/Drizzle: control-plane and thin projection data only; no local recipe/product/order/memory store.

The provider abstraction and registry remain: they isolate provider authentication from the core flow. MCP tool discovery, product and basket operations are handled by the managed workflow after authorization and approval.

The chat entry creates one workflow from the first request and immediately opens that workflow. Further additions, replacements and approvals happen inside the workflow; the chat composer is not used to create another workflow until the user exits and starts a new chat session.

MiyKo may cache provider reads or the latest observed workflow/provider status to reduce repeated requests. These are read optimizations only: they are not authoritative state, are not approval evidence and must be revalidated by the managed workflow before a provider mutation.

## Security

Authentication and authorization are enforced at the API and database RLS boundary. Email/password authenticates a MiyKo user only. The household owner connects Silpo in the provider browser through OAuth 2.1 Authorization Code + PKCE; MiyKo stores the resulting owner-scoped credentials encrypted and binds that account once to the household. A provider mutation requires an authenticated owner/admin command or their approval. The API supplies the current access token to each local LangGraph run as runtime-only context, never as graph state or Mem0 memory. Missing integrations fail explicitly; there are no mock or silent fallback paths.

## Database

The database package contains one clean `drizzle/0000_initial.sql` baseline. It is not executed by API startup. Use the separate migration connection when the database owner explicitly applies it.
